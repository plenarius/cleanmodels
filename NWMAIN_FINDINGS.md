# nwmain-linux static-analysis findings (running list)

Static analysis only, from `nwmain-linux` (unstripped x86-64, Steam NWN:EE, 2026-10-11).
Addresses are nm/file vaddrs. Ghidra shows them +0x100000 (PIE load base).
Decompiles, the Ghidra project and the scripts live in `~/dev/nwn/nwmain-analysis/` (see its README).
Status: CONFIRMED (read in code), UNVERIFIED (inferred or incomplete). Decision column is ours to fill in.

## Pipeline

`MdlNodeTriMesh::InternalPostProcess` (0x4577c0), when the node has no GPU vertices yet, runs:
`ProcessVerts` -> `InternalGenVertices` (virtual, vertex dedup + degenerate strip) -> `BuildNeighborLists`
-> `BuildVertexIndices` -> `GenerateVertexData` -> `CalculateTangentSpaceBasis`.
If GPU vertices already exist (binary load), only `CalculateTangentSpaceBasis` runs.
AnimMesh, DanglyMesh and Skin have their own variants of the same chain.

## Decompiler (binary.go) check against these findings

- Reads the GPU vertex arrays directly and faces as GPU indices, which matches the engine layout (finding 12). OK
- Tangents: vec3 stream plus +-1 handedness float, default +1 when absent. Matches findings 11 and 12. OK
- Colors: bytes / 255. Matches the engine's byte encoding. OK
- Face adjacency and plane distance are skipped on read. The compiler writes 0xFFFF adjacency, but game binaries carry real values (finding 15). The engine recomputes them at load, so this is probably fine.
- Smoothing group is not stored in binaries, so it decompiles to 0 and the stored normals carry the smoothing. Expected.
- Controllers and animations were not examined in this pass. Skin and dangly are compared in the sections below.

### Answers to the open questions

1. **Where the bind data is computed.** At the first draw of the first instance (finding 20), from the instance's tree (21), which for an attached part is the creature skeleton (22). Not at load and not at write time; `compilemodel` writes the bound state. Bones are numbered by first use over the final GPU vertices (26).
2. **The sign.** `operator-` negates w only, so the engine's inverse is the negated conjugate (24). Bind lists never go through the `orientation` parser.
3. **A weight on a bone that is not a node.** The engine leaves it out and the vertex's remaining weights are renormalised by the perspective divide (25, 26). Leftover slots can hold pool garbage; a garbage weight > 0 with a garbage index would distort that vertex. Ours points at an out-of-range uniform (undefined behaviour, rendered fine on the test machine).
4. **What tears one skinned part while the rest is fine.** Read from the code, any of these does:
   - a. **A binary skinned part whose tree positions do not match the creature skeleton.** Each bone then picks up the transform of whichever skeleton node has its number, so neighbouring vertices weighted to different bones fly apart into stretched sheets. Positions past the skeleton's size are skipped, and those bone slots keep the matrices of the previous skin drawn that frame. Every binary skinned part that cleanmodels compiles is in this state unless its own tree matches the skeleton (22).
   - b. **A vertex with no applied weight**: every slot is 0, negative, or names a bone that did not resolve. Its position is (0,0,0,0) in clip space, and every triangle touching it is drawn as a sliver or sheet. This is what an ASCII produced by decompiling an engine-compiled skinned part gives (23).
   - c. **An ASCII skin bound on a different skeleton.** The bind happens once per loaded model, on the first creature that draws it (20). A skinned head first drawn on one skeleton and later shown on another with a different node order is wrong on the second.

   The body is unaffected in all three cases because each skin is bound and drawn on its own. Without the model, (a) and (b) are the most likely, since the report came to cleanmodels and both are cleanmodels gaps (inferred; not reproduced on her model). Her `skin_summary` output will tell them apart: a head named `p??#_head###` (an attached part) plus a binary in her hak points to (a); bones named `_` or after the model's own mesh nodes points to (b).
5. **Animation block size.** Not read in this pass. The animation writer was not reached; it does not bear on the tear.
6. **Uninitialised fields.** `boneconstantindices` and dropped-influence slots only (27).
7. **ASCII render vs `compilemodel`.** The same in-memory state: the gate requires the bind of finding 20 to have run, and `compilemodel` writes it. The serialiser itself (`IODispatcher::Write`, `FUN_005bc560`) was not read.

### Fixes (2026-10-14)

- **Attach point.** Read empirically, then from data: hanging `pmh0_neck001` from `neck_g` reproduces all 56 engine bind entries (worst difference 7e-5; the next-best node is off by 0.06). The part-to-node table is `capart.2da` (`NECK` to `neck_g`, `CHEST` to `torso_g`, `ROBE` to `root`, ...); the head is not in it, and the engine attaches it to `head_g`, the only node name besides `lfoot_g`/`rfoot_g` among the binary's strings. Compile reads `capart.2da` from the same places it searches for skeletons (the model's folder, `--resource-dir`/`--supermodel-dir` folders and haks, the game install), first found wins, so a custom skeleton's own table (a report had `FOOTR` to `j_kao`) is honoured; the built-in stock table is only the fallback when none is found (fixed after v4.4.0, which always used the stock table). `ROBE` hanging from the skeleton's root, and whether a part root with its own transform adds it (the HD neck's root is identity), are not confirmed against an engine compile.
- **Decompiler**, **compiler** and the **`skin_part_binding`** check are done as described in findings 22 and 23. `skin_unknown_bone` no longer reports a body part's skeleton bones.
